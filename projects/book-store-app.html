Book Store Application

A desktop book store app built by a team of three in Java. We designed the class structure in UML first, then implemented it in NetBeans with a JavaFX interface. Final grade: 94 percent.

When
May to June 2024
Role
Three-person team: design, implementation, coordination
Stack
Java, JavaFX, UML, NetBeans 8.2

Design first

The brief was an object-oriented book store: customers, books, orders, and the state that ties them together. Before writing code we drew the class diagram and worked out which design patterns fit. That upfront design meant the three of us could implement separate classes and have them fit together, because the interfaces were already agreed.

ModellingUML class diagrams and design patterns before implementation
LanguageJava in NetBeans IDE 8.2
InterfaceJavaFX user interface on top of the model
ResultFully functional submission, 94 percent

Use cases

We wrote the use cases before the class diagram. There are two actors, and each one has a small, well-defined set of things they can do.

Owner: loginCredentials checked against the stored owner account before the dashboard opens
Owner: add bookEnter a name and price. Missing fields prompt again, a non-numeric price shows an error
Owner: add customerEnter a username and password. Empty fields prompt again, a duplicate username is rejected
Customer: loginCredentials checked against stored customer accounts
Customer: view booksEvery book in the inventory listed with a checkbox. Selections build the cost screen
Customer: buyPay in full, or redeem points first and pay the remainder. Points and status update after each purchase

State pattern

Customers have a status, silver or gold, decided by the points they have accumulated and the money they have spent. Purchasing behaves differently depending on that status, and the status changes at run time, so this is the textbook case for the State pattern.

Each status is its own state class with the purchasing behaviour for that tier inside it. The customer holds a reference to its current state and delegates to it, which removes the conditional logic that would otherwise be scattered through the customer class. When a customer reaches 1,000 points the state object swaps itself for gold, and the customer class does not change at all.

The other reason we chose it is that it scales. Adding a bronze or platinum tier later means writing one new state class, not editing every place that checks status. That costs a few more classes than a flag would, but the code is easier to read and safer to extend.

Implementation

The core model is plain Java classes that follow the UML. The JavaFX layer sits on top and talks to the model through its public interface, so the UI could change without touching the business logic. Login, the owner dashboard, the book list, and the cost screen are separate JavaFX views.

Working as a team

Most of the grade came from the app working, but a lot of the work was coordination. We split the class diagram into ownership areas, agreed on method signatures early, and integrated often so merge problems stayed small. That habit of agreeing on interfaces first is one I have carried into hardware projects, where the interface is a wiring diagram instead of a method signature.
