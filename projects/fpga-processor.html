Processor on an FPGA

A small processor described in VHDL and run on an Altera DE-series board. FSM control unit, ALU, memory, and an instruction set that executes arithmetic and data movement on real hardware.

When
September to November 2024
Role
Two-person team: design, VHDL, testbenches
Stack
VHDL, Quartus II, Altera DE-series FPGA

Building blocks

Before the processor existed we built and verified its pieces on their own. Each one was designed in Quartus II, simulated, and checked against expected waveforms before being trusted in the larger design.

Finite state machinesState machines designed and simulated in Quartus II before integration
RegistersClocked registers designed and simulated as standalone modules
ALUArithmetic and logic operations selected by opcode
MemoryInstruction and data storage addressed by the control unit

The processor

The control unit is an FSM that steps each instruction through fetch, decode, and execute. On decode it selects the ALU operation, the register file ports, and whether memory is read or written. The datapath moves values between the register file, the ALU, and memory under that control, so a program loaded into memory runs instruction by instruction on the board.

Splitting control from datapath early made the design much easier to reason about. When something went wrong it was almost always clear whether the bug was in what the FSM asked for or in what the datapath did with the request.

Verification

Every module had a testbench, and the full processor had one that ran short programs and checked register and memory contents at the end. The most useful testbenches were the ones that stressed timing: instructions that read a register the cycle after it was written, and memory accesses back to back. Those caught issues that the individual module simulations had passed, and fixing them is what made the design execute reliably on the FPGA rather than only in simulation.

What I learned

  • Timing is the design. A module that works in isolation can still fail when its inputs arrive a cycle late. Thinking in clock edges, not just logic, became the habit.
  • Testbenches earn their time back. Writing them felt slow at first. They ended up being the fastest way to find bugs.
  • Hardware makes abstractions concrete. Fetch, decode, and execute stopped being lecture terms once they were states in an FSM I could probe on a board.
